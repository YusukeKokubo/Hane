# はまりどころ

前に踏んだ落とし穴と、その回り道を残す。触る場所の節だけ読めばよい。

## 画面とキー操作

- **`ViewThatFits` を使わない。** 候補を全部作って、中身が変わるたびに全部測り直す。タブバーで使っていたときは、ページを移るたびにメインスレッドが0.1秒ほど取られていた（取り除いて三分の一）。タブを縮めるか横に流すかは、縮めきった幅を足し算で出して選んでいる。
- **入力欄を標準ツールバーに置かない。** `.toolbar` の中の `TextField` には `FocusState` が効かず、Cmd+L が動かなくなる。そのためタイトルバーを隠し、タブバーとナビゲーションの段をウインドウの中身として並べている。タブバーがタイトルバーを兼ねるので、左端の信号機ボタンの余白と、右端のウインドウを掴むための余白を削らない。
- **起動直後のフォーカスは一度では入らない。** ウインドウが前面に出る前の要求は黙って捨てられるので、`AddressBar` は入るまで短くやり直している。
- **Cmd+W をタブに割り当てる仕組み。** メニューの「タブを閉じる」を標準の「閉じる」より前（`.newItem` の位置）に置くことで先に拾わせている。順番を変えるとウインドウごと閉じるようになる。その代わり設定の窓が手前にあっても ⌘W がタブを閉じてしまうので、`closeTab` は手前の窓が本体の窓（識別子 `main`）でなく、シートやポップオーバーでもなければ、その窓を閉じる。
- **中身が変わるメニュー項目のショートカットは当てにしない。** SwiftUI はメニューの中身を開く直前まで作り直さないので、起動後に増えた項目のキーはメニューを一度開くまで効かない。プロファイルの ⌃1〜9 は、このため `LocalShortcuts`（AppKitの局所モニタ）で拾っている。⌘1〜9 のように起動時から決まっている項目は問題ない。局所モニタで拾ったキーはページへ届かないので、ページがよく使う組み合わせは取らない（⌥⌘数字は Google ドキュメントや Notion の見出しに使われていて、一度取ってしまった）。
- **⌘1〜8 はバーの左から数える。** ブックマークとフォルダとタブを、見えている一列のまま数える（フォルダなら一覧を開け閉めする）。番号が見た目の並びとずれないようにするため。⌘9 は最後の普通のタブ。前後のタブは ⇧⌘[ / ⇧⌘] と ⌃Tab / ⌃⇧Tab で、メニューの項目にはキーが一つしか付かないので ⌃Tab は `LocalShortcuts` が拾う。
- **バーのドラッグは専用の型で運ぶ。** `BarDragItem` の型 `local.personal.browser.bar-item` は `Support/Info.plist` で宣言している。文字列で運ぶと、ページの入力欄に落としたとき文字として入ってしまう。

## タブとページ

- **ページの解放。** `Tab` はページ（`Page`）を要るあいだだけ持つ。閉じるときと眠らせるときは `Page.tearDown()` で見張りと案内役を外してから手放す。案内役（navigation / UI delegate）は `Page` とは別の小さな型にして弱く持たせ、Web ビューから `Page` やタブ管理へ循環させない。`closedTabReleasesItsPage` と `sleepingReleasesThePageAndWakingRestoresHistory` のテストが見張っている。
- **しばらく使っていないタブは眠らせる。** 画面から外れて `BrowserSettings.tabSleepDelay`（30分）経ったタブは、次に選択が変わったとき `TabStore.sleepIdleTabs` がページを手放す（ページのプロセスが返る。タブ1枚あたり十数MB）。決めるのは選択が変わったときだけで、タイマーは使わない。読み込み中のタブ、音や動画を流している・カメラやマイクを使っているタブは眠らせない。眠らせる前に `WKWebView.interactionState`（戻る・進むの履歴と今の位置。中身は WebKit だけが読める）を控えに取り、選ばれたら新しいページにそれを戻すので、履歴は残る。書きかけの入力やスクリプトで作ったページの中の状態は読み込み直しで消える。控えを読めなかったときはアドレスから開き直す。
- **ブックマークはArcのピン留めと同じ考え方。** 押すと新しいタブを作らずその場でページを開き、閉じてもブックマークは残る。開いていないブックマークはタブを持たない。開いたブックマークのページも、普通のタブと同じく眠らせる。ブックマークはプロファイルごとに `bookmarks.json` に保存し（置き場は「プロファイル」の節）、使い捨ての実体（`dev` など）では保存しない。テストで `TabStore` を作ると保存しないブックマークになる。
- **閲覧状態は変化を拾って書き出す。** `TabStore` が `withObservationTracking` で開いているページの並び・アドレス・題名・選択を見張り、変わったら書き出す（同じ中身なら書かない）。タイマーは使わない。終了直前にも `BrowserApp` から一度書く。プロファイルごとに `session.json` に保存し、使い捨ての実体とテストではファイルに書かずメモリに持つ（プロファイルを行き来したときに戻すため）。ページごとに戻る・進むの履歴の控え（`interactionState`）も書くので、再起動しても戻れる。控えは見張りの中では取らず、書き出すときだけ取る（見張るたびに全タブぶん取ると重い）。
- **macOS の再開は切ってある（`restorationBehavior(.disabled)`）。** 任せるとウインドウの状態が変わるたびに窓全体の画像を取って保存し、アプリ本体が25MBほど膨らんだまま戻らない（その瞬間は倍）。タブは閲覧状態で戻すので要らない。その代わり窓の位置と大きさは戻らなくなるので、`WindowFrameMemory` が AppKit の自動保存で覚える。名前はプロファイルごとに分け、開発用の実体が普段使いの窓を動かさないようにしている。
- **戻したタブは選ばれるまでページを作らない。** 一斉に読み込むとタブの数だけ WebContent プロセスが立ち上がるため。眠らせたタブと同じ扱いで、`TabStore.selectedID` の `didSet` で起こす。行き先は `Tab.url` で読む（ページを持たないタブや、読み込みに失敗してページのアドレスが空のタブでも返す）。なお、読み込んでいない Web ビューはページのプロセスを立ち上げず、アプリの中で1枚あたり30KBほどだった。
- **閲覧履歴は少し遅れてまとめて書く。** 数千件を訪問のたびに書き直さないよう、変化から数秒待って書き出し、終了直前にも書く（待つのは変化のあった後の一度きりで、常駐するタイマーではない）。保存先はプロファイルごとの `history.json`（使い捨ての実体では保存しない）。上限は5000件で、超えたら最後に訪れたのが古いものから捨てる。
- **アドレスバーで補うのは、打って訪れたページとサイトの入口だけ。** リンクで通っただけの深いページまで補うと、打つたびに思わぬ所へ飛ばされるため。「打って訪れた」は `Tab.open(typed:)` を通った読み込みで、検索結果のページは数えない。補った続きは `TextSelection` で選択した状態で入れ、打ち足すと置き換わる。打った部分を消している間は補わない（補うと消した文字が戻ってくる）。
- **プロセスプールは全タブで一つにしている（`SharedConfiguration`）。** `WKWebViewConfiguration` を別々に作るとプールも別々になる（`WKProcessPool` は「複数作っても意味がない」として非推奨だが、macOS 26 でも実際に分かれた）。プールが別々だと、別のサイトへ移ったとき「戻る」用に残すページ（プールごとに2つ）と先に立ち上げる予備のプロセス（プールごとに1つ）がタブの数だけ溜まり、6枚で別のサイトへ一度ずつ移るとページのプロセスが18個になった（共有すると8個）。そこで元になる設定を一つだけ作り、プロファイルごとにそれを写して使う。写した設定はプールと環境設定（`WKPreferences`）を元と同じものに保つので、設定の窓で変えた値（ポップアップを止めるか）も開いているタブにその場で効く。`pagesShareOneProcessPool` のテストが見張っている。テストでも環境設定は一つきりなので、変えたテストは前の値に戻す。
- **`WebPage`（WebKit for SwiftUI）をやめた経緯。** 以前はページを `WebPage`、表示を SwiftUI の `WebView` で組んでいた。`WebPage` は設定にプールや `WKPreferences` を渡す口がなく、ページの案内役（`WKUIDelegateAdapter`）は `window.open` の窓を作る手続きを持たず、戻る・進むの履歴を書き出す口もない。前の二つは `WKWebViewConfiguration` の `init` の差し替えと、案内役の型への手続きの追加という実行時の裏技で埋め、外れていないかを起動後の最初のページで確かめる仕組みまで持っていた。最後の一つは埋められず、再起動やタブを眠らせると履歴が消えるため、`WKWebView` を `Page` で包む作りに移した。代わりに、SwiftUI にそのまま載る手軽さを手放し、Web ビューの値を Observable に写す層（`Page`）と画面に置く部品（`PageView`）を自分で持つことになった。`WebPage` が黙って面倒を見ていた所もこちらで埋める必要があり、移したときには、読み終えた知らせの時点で題名がまだ空のことがある件と、macOS の `takeSnapshot` が見えている所しか描かない件を直した。`WebPage` にプールと環境設定を渡す口、`window.open` の受け口、履歴の書き出しが揃えば戻すことを考えてよい。逆に、`WebPage` では起きなかった不具合が普段使いで続くようなら、この判断を見直す。
- **`window.open` はページの案内役が受ける。** `Page` の UI delegate の `createWebViewWith` から `PopupWindows.create` を呼ぶ。大きさを指定して開いたもの（ログインの小窓など）は、WebKit が渡した設定で `WKWebView` を作って AppKit の小窓（`PopupWindow`）に置き、ページへ返す。返さないと `window.opener` がつながらず、Google などのログインは「窓を開けなかった」として止まる。大きさの指定がないものは新しいタブで開き、ページへは null を返す。小窓を閉じるときは Web ビューを窓から外す。閉じた窓は AppKit がしばらく掴んでいて、中に置いたままだとページが残り、開いた側から `window.closed` が false に見えた。止めるかどうかは WebKit がその手前で `javaScriptCanOpenWindowsAutomatically` を見て決めるので、止めていれば操作の中から開いたものしか届かない。スクリプトが押した `target="_blank"` のリンクも同じく WebKit が止める。`eval` と `click` は WebKit が操作の中として扱うので、止めていても開く。`popupsFollowTheSetting` と `sizedPopupsOpenInTheirOwnWindow` のテストが見張っている。設定はプロファイルによらずアプリ全体で一つで、普段使いの実体だけ `Browser/settings.json` に書き、使い捨ての実体とテストでは保存しない。

## プロファイル

- **実体とプロファイルは別のもの。** 実体（プロセス）を分けるのは開発や計測で普段使いに触れないためだけで、環境変数 `BROWSER_INSTANCE`（dev、bench など）で選ぶ。名前を付けた実体は何も保存しない使い捨てで、操作用ソケットは `Browser/instances/<名前>/control.sock`、広告ブロックのコンパイル結果は `~/Library/Caches/Browser/instances/<名前>` に分ける。前は `BROWSER_PROFILE` が実体とプロファイルを兼ね、プロファイルごとに実体を起こして一つの窓に見せかけていたが、窓の枠の受け渡しや前に出る権利の譲り合いなど後始末が積もったのでやめた。前の変数（`BROWSER_PROFILE`、`BROWSER_EPHEMERAL`）が付いていると、アプリも `browserctl` も止まる。黙って普段使いの実体を相手にしないため。
- **プロファイルは一つの窓の中で切り替える。** 開くのは一度に一つで、`BrowserModel` が今のプロファイルの `TabStore` を持つ。切り替えると今の `TabStore` を `shutDown()`（閲覧状態を書き出してから全ページを閉じ、以後は新しいタブも閲覧状態の書き出しも断る）し、離れるプロファイルが開いた小窓も閉じて、移る先の `TabStore` を閲覧状態から作る（選んでいたページだけ読み込む）。離れたプロファイルのページは生かしておかない（切り替えは頻繁でないため）。ページの判断は非同期なので、離れたあとに古い `TabStore` へ新しいタブの頼みが届くことがあり、`shutDown()` の印で断っている。窓・メニュー・`LocalShortcuts`・`ControlService` は起動時の `TabStore` を掴まず、使うたびに `model.store` を読む（掴むと切り替えたあと古いプロファイルを相手にする）。掴み残しは `switchingReleasesThePagesOfTheProfileLeft` のテストが見張る。
- **プロファイルの持ち物は、一度開いたら実体が終わるまで捨てない。** ブックマーク、履歴、閲覧状態、サイトデータの置き場（`ProfileData`）を名前で引けるように持ち続け、戻ったときに同じものを使う。同じファイルを二つのストアが書き合わないためと、使い捨ての実体でも閲覧状態を戻せるようにするため。
- **置き場。** 普段使いの実体では、`default` の持ち物は `~/Library/Application Support/Browser/` 直下（分ける前からの場所）、それ以外は `profiles/<名前>/` に置く。サイトデータは `default` が WebKit の既定、登録したものは一覧（`Browser/profiles.json`）に残した識別子で `WKWebsiteDataStore(forIdentifier:)` に分ける（同じ識別子なら同じものが返る）。一覧には最後に開いたプロファイル（`lastOpened`）も残し、次の起動でそれを開く。設定と隠した要素はアプリ全体で一つで、`Browser/` 直下にだけ置く。テストで `forIdentifier` を使うと `~/Library/WebKit` の下に本物の置き場ができて消せないので、テストのサイトデータは `.nonPersistent()` にする（`BrowserModel` の `keepsSiteData: false`）。
- **使い捨ての実体のプロファイル。** 登録した一覧は見せず、作った名前はその実体の中だけに持ち、どのプロファイルも何も保存しない（サイトデータは名前ごとの `.nonPersistent()`）。
- **裏に起こす実体には記述子を渡さない（`spawnDetached`）。** 渡すと呼んだ側の操作用ソケットを子が握り、呼んだ側が終わったあとも同じパスへの接続を子が受けたまま答えない。`browserctl` は応答を待ち続け、`verify.sh` が始めの `quit` で7分止まった。

## 広告ブロック

- **広告ブロックは WebKit のコンテンツブロッカーで行う。** 判定はページのプロセスの中で WebKit がするので、アプリ側で常に動く処理はない。同梱のリスト（EasyList と AdGuard Japanese）を起動時に訳してコンパイルするのは中身か `FilterList.version` が変わったときだけで（数秒）、ふだんは `WKContentRuleListStore` から引くだけ。訳し方を変えたら `FilterList.version` を上げる。普段使いの実体は WebKit の既定の置き場、使い捨ての実体は `~/Library/Caches/Browser/instances/<名前>` に置くので、`verify.sh` の初回はコンパイルを待つ。リストはアプリ全体で一つで、プロファイルを切り替えても作り直さない。
- **WebKit のルールは1リスト15万件まで、ひとつでも受け付けないルールがあるとリスト全体が落ちる。** 訳せない書き方は捨てる方へ倒し、`bundledListsCompile` のテストで同梱のリストが実際にコンパイルできるかを見張っている。例外（`ignore-previous-rules`）は同じリストで前にあるルールしか取り消せないので、例外は最後に並べる。
- **右クリックのメニューには項目を足せない。** WebKit for SwiftUI の `webViewContextMenu` は標準の項目（コピー、調べる、Webインスペクタなど）をすべて置き換えてしまう。そのため要素を隠す操作は、ページ内のスクリプトで ⌥ 付きの右クリックだけを拾っている。子フレームの中なら `postMessage` で親へ知らせてフレームごと選ばせる。`browserctl` からは、合成した `contextmenu` 事象（`altKey: true`）と `press` で同じ流れを試せる。

## browserctl と窓まわりの操作

- **SwiftUI はアクセシビリティの木を問われるまで作らない。** `open` で起動すると常駐する何かが問い合わせて木ができるが、直に起動すると（`verify.sh`）中から辿っても空のまま。`WindowElements` は外の道具と同じ API で自分に一度問い合わせて作らせている。作らせても、何もしていない間の起床回数とメモリは変わらなかった。
- **窓まわりの操作で、アプリを止めてしまうもの。** 選択欄を押す、右クリックのメニューを出すと、閉じるまでメインスレッドが止まって応答を返せない。そのため `ui-menu` はメニューを出さずに中身を引いて項目の動作を直に呼び、`ui-click` は選択欄を断る。ボタンは押されると離す事象を自分で待つので、離す事象を先に待ち行列へ積んでから押す。選択欄は選択欄の動作を送っても SwiftUI の値が変わらず、項目の動作を呼ぶ必要がある。
- **窓まわりで、作った事象では確かめられないもの。** ドラッグは始まらない（運ぶ中身を載せた情報を落とし先へ直に渡す方法も試したが、SwiftUI は受け付けず、その後の描画でアプリが落ちた）。並べ替えは `TabStore.drop` の単体テストで見る。`onHover` はアプリが前面のときしか効かないので、裏にいるときの `ui-hover` は乗せたときの表示を出せない（`verify.sh` はそのとき skip と出す）。
- **シートが出ていると終了が黙って取りやめになる。** `quit` は先にシートを閉じてから終える。終わったつもりで古い版が動き続け、作り直した版を試したつもりになることがあった。また、起動していないときの `quit` は何もしない（前は起こしてから止めていて、作り直している最中の古い版が動き出すことがあった）。

## テスト

- **テストはネットワークに出さない。** HTMLは一時ファイルに書いて `file://` で開く。`data:` や検索語はアドレスの解釈に巻き込まれやすい。
- **`file://` のページでは例外の中身が「Script error.」に潰れる。** WebKitの仕様で、http(s) のページでは普通に取れる。
