# はまりどころ

前に踏んだ落とし穴と、その回り道を残す。触る場所の節だけ読めばよい。

## 画面とキー操作

- **`ViewThatFits` を使わない。** 候補を全部作って、中身が変わるたびに全部測り直す。タブバーで使っていたときは、ページを移るたびにメインスレッドが0.1秒ほど取られていた（取り除いて三分の一）。タブを縮めるか横に流すかは、縮めきった幅を足し算で出して選んでいる。
- **入力欄を標準ツールバーに置かない。** `.toolbar` の中の `TextField` には `FocusState` が効かず、Cmd+L が動かなくなる。そのためタイトルバーを隠し、タブバーとナビゲーションの段をウインドウの中身として並べている。タブバーがタイトルバーを兼ねるので、左端の信号機ボタンの余白と、右端のウインドウを掴むための余白を削らない。
- **起動直後のフォーカスは一度では入らない。** ウインドウが前面に出る前の要求は黙って捨てられるので、`AddressBar` は入るまで短くやり直している。
- **Cmd+W をタブに割り当てる仕組み。** メニューの「タブを閉じる」を標準の「閉じる」より前（`.newItem` の位置）に置くことで先に拾わせている。順番を変えるとウインドウごと閉じるようになる。その代わり設定の窓が手前にあっても ⌘W がタブを閉じてしまうので、`closeTab` は手前の窓がプロファイルを出している本体の窓でなく（設定の窓や、⌘N で開いてプロファイルを選ぶ前の窓）、シートやポップオーバーでもなければ、その窓を閉じる。
- **中身が変わるメニュー項目のショートカットは当てにしない。** SwiftUI はメニューの中身を開く直前まで作り直さないので、起動後に増えた項目のキーはメニューを一度開くまで効かない。プロファイルの ⌃1〜9 は、このため `LocalShortcuts`（AppKitの局所モニタ）で拾っている。⌘1〜9 のように起動時から決まっている項目は問題ない。局所モニタで拾ったキーはページへ届かないので、ページがよく使う組み合わせは取らない（⌥⌘数字は Google ドキュメントや Notion の見出しに使われていて、一度取ってしまった）。
- **⌘1〜8 はバーの左から数える。** ブックマークとフォルダとタブを、見えている一列のまま数える（フォルダなら一覧を開け閉めする）。番号が見た目の並びとずれないようにするため。⌘9 は最後の普通のタブ。前後のタブは ⇧⌘[ / ⇧⌘] と ⌃Tab / ⌃⇧Tab で、メニューの項目にはキーが一つしか付かないので ⌃Tab は `LocalShortcuts` が拾う。
- **バーのドラッグは専用の型で運ぶ。** `BarDragItem` の型 `local.personal.hane.bar-item` は `Support/Info.plist` で宣言している。文字列で運ぶと、ページの入力欄に落としたとき文字として入ってしまう。
- **窓を動かすのはタブバーの空いた所だけに任せる。** タブバーはタイトルバーの位置にあり、AppKit はその一帯を掴むと窓を動かすので、タブやブックマークを引きずってもドラッグが始まらず窓が動いていた（`windowBackgroundDragBehavior` を切っても、タイトルバーの位置なので動く。項目を `Button` の形にしても変わらない）。そこで窓の `isMovable` を切り（`StillWindow`）、タブバーの背面に置いた `WindowDragGesture` だけで動かす（`WindowDragArea`）。項目が手前にあるので、ドラッグは項目が受ける。裏にいる窓でも一度目で掴めるよう `allowsWindowActivationEvents` を付けている。動かせない窓は画面を外してもシステムが寄せてくれないので、画面の構成が変わったとき、上端がどの画面にも見えていなければ自分で戻す。作った事象（`hanectl`）では窓が動くかを確かめられず、`CGEvent` で本物のマウスを動かして確かめた。
- **文字のキーでの操作（`KeyNavigation`）はページの中で拾う。** 入力欄に打っているかを正しく知っているのはページだけで、局所モニタで拾うと入力欄の文字まで横取りするため。専用の実行環境のスクリプトが `window` の capture で先に受け、`isTrusted` でないキーは無視する（ページが合成したキーでタブを閉じたり開いたりさせないため）。タブの移動や戻る・進むだけアプリへ知らせ、`Page.Event.keyCommand` からタブ管理へ渡る。使わないサイトの一覧は設定にあり、変えると開いているページのスクリプトへその場で伝える（`KeyNavigation.policy`）。ページの最初の可否はスクリプトがアプリに尋ね、アプリは WebKit が知っているフレームの出どころで答える。
- **ページにキーボードのフォーカスを渡すのは `TabStore.pageFocusRequest`。** アドレスバーで Return や Esc を押したあとと、タブを移ったあとに増やし、見えている `PageView` が受ける。渡さないとフォーカスがアドレスバーに残り、`j` を打つとアドレスバーに入っていた。起こしたばかりのページは窓に載る前なので、載ってから渡す。
- **テストで Web ビューを窓に載せてキーを送るときは、先に `makeFirstResponder` してから窓を前に出す。** 逆にすると、AppKit が Tab で入ったのと同じ扱いで Web ビューへフォーカスを送り、WebKit がページの最初の入力欄にフォーカスを入れる（キーが入力欄の文字になる）。本物のキーとして届くので `isTrusted` も立つ。

## タブとページ

- **ページの解放。** `Tab` はページ（`Page`）を要るあいだだけ持つ。閉じるときと眠らせるときは `Page.tearDown()` で見張りと案内役を外してから手放す。案内役（navigation / UI delegate）は `Page` とは別の小さな型にして弱く持たせ、Web ビューから `Page` やタブ管理へ循環させない。`closedTabReleasesItsPage` と `sleepingReleasesThePageAndWakingRestoresHistory` のテストが見張っている。
- **しばらく使っていないタブは眠らせる。** 画面から外れて `BrowserSettings.tabSleepDelay`（30分）経ったタブは、次に選択が変わったとき `TabStore.sleepIdleTabs` がページを手放す（ページのプロセスが返る。タブ1枚あたり十数MB）。決めるのは選択が変わったときだけで、タイマーは使わない。読み込み中のタブ、音や動画を流している・カメラやマイクを使っているタブは眠らせない。眠らせる前に `WKWebView.interactionState`（戻る・進むの履歴と今の位置。中身は WebKit だけが読める）を控えに取り、選ばれたら新しいページにそれを戻すので、履歴は残る。書きかけの入力やスクリプトで作ったページの中の状態は読み込み直しで消える。控えを読めなかったときはアドレスから開き直す。
- **ブックマークはArcのピン留めと同じ考え方。** 押すと新しいタブを作らずその場でページを開き、閉じてもブックマークは残る。開いていないブックマークはタブを持たない。開いたブックマークのページも、普通のタブと同じく眠らせる。ブックマークとタブの結びつきは `TabStore.bookmarkTabs` だけで持ち、`Tab` はブックマークを知らない（二か所で持つと、ピン留めや削除のたびにそろえる必要があった）。ブックマークはプロファイルごとに `bookmarks.json` に保存し（置き場は「プロファイル」の節）、使い捨ての実体（`dev` など）では保存しない。テストで `TabStore` を作ると保存しないブックマークになる。
- **閲覧状態は変化を拾って書き出す。** `TabStore` の持つ `SessionRecorder` が `withObservationTracking` で開いているページの並び・アドレス・選択と、ページを移って最初に題名が届いたこと（`Tab.titleArrivals`）を見張り、変わったら書き出す（同じ中身なら書かない）。題名そのものは見張らない。未読の数などで題名を書き換え続けるページがあり、見張るとそのたびに全タブぶんの控えを取って書き出していた（題名が13秒に9回変わるページで書き出しが4〜5回）。移ってから後の題名の変化は次の書き出しに乗る。題名は読み終えた知らせの後に届くことがあるので、読み込みの終わりを見張っても間に合わない。タイマーは使わない。終了直前にも `HaneApp` から一度書く。プロファイルごとに `session.json` に保存し、使い捨ての実体とテストではファイルに書かずメモリに持つ（プロファイルを行き来したときに戻すため）。ページごとに戻る・進むの履歴の控え（`interactionState`）も書くので、再起動しても戻れる。控えは見張りの中では取らず、書き出すときだけ取る（見張るたびに全タブぶん取ると重い）。
- **macOS の再開は切ってある（`restorationBehavior(.disabled)`）。** 任せるとウインドウの状態が変わるたびに窓全体の画像を取って保存し、アプリ本体が25MBほど膨らんだまま戻らない（その瞬間は倍）。タブは閲覧状態で戻すので要らない。その代わり窓の位置と大きさは戻らなくなるので、`WindowFrameMemory` が AppKit の自動保存で覚える。名前は実体とプロファイルごとに分け（標準のプロファイルは窓が一枚きりだった頃の名前のまま）、開発用の実体が普段使いの窓を動かさないようにしている。窓の中でプロファイルを切り替えたときは、窓を動かさずに今の位置を移る先の名前で覚え直す。閉じた窓は AppKit がしばらく掴んでいて名前を握ったままになるので、閉じるときに名前を外す。
- **戻したタブは選ばれるまでページを作らない。** 一斉に読み込むとタブの数だけ WebContent プロセスが立ち上がるため。眠らせたタブと同じ扱いで、`TabStore.selectedID` の `didSet` で起こす。行き先は `Tab.url` で読む（ページを持たないタブや、読み込みに失敗してページのアドレスが空のタブでも返す）。なお、読み込んでいない Web ビューはページのプロセスを立ち上げず、アプリの中で1枚あたり30KBほどだった。
- **閲覧履歴は少し遅れてまとめて書く。** 数千件を訪問のたびに書き直さないよう、変化から数秒待って書き出し、終了直前にも書く（待つのは変化のあった後の一度きりで、常駐するタイマーではない）。題名だけの変化では書き出しを予約しない（題名を書き換え続けるページで、数千件を数秒おきに書き直し続けるため）。題名は次の訪問か終了時の書き出しに乗る。保存先はプロファイルごとの `history.json`（使い捨ての実体では保存しない）。上限は5000件で、超えたら最後に訪れたのが古いものから捨てる。
- **アドレスバーで補うのは、打って訪れたページとサイトの入口だけ。** リンクで通っただけの深いページまで補うと、打つたびに思わぬ所へ飛ばされるため。「打って訪れた」は `Tab.open(typed:)` を通った読み込みで、検索結果のページは数えない。補った続きは `TextSelection` で選択した状態で入れ、打ち足すと置き換わる。打った部分を消している間は補わない（補うと消した文字が戻ってくる）。
- **プロセスプールは全タブで一つにしている（`SharedConfiguration`）。** `WKWebViewConfiguration` を別々に作るとプールも別々になる（`WKProcessPool` は「複数作っても意味がない」として非推奨だが、macOS 26 でも実際に分かれた）。プールが別々だと、別のサイトへ移ったとき「戻る」用に残すページ（プールごとに2つ）と先に立ち上げる予備のプロセス（プールごとに1つ）がタブの数だけ溜まり、6枚で別のサイトへ一度ずつ移るとページのプロセスが18個になった（共有すると8個）。そこで元になる設定を一つだけ作り、プロファイルごとにそれを写して使う。ただしプールは初めて読まれたときに作られるので、元でまだ作っていないうちに写すと、写した先でめいめいが別のプールを作る（macOS 27 で、プロファイル二つの窓でそれぞれ三つのサイトを渡り歩くとページのプロセスが8個、作っておくと5個）。そこで元の設定を作るときにプールを一度読んでおく（読み口は非推奨で警告になるので名前で読む）。写した設定はプールと環境設定（`WKPreferences`）を元と同じものに保つので、設定の窓で変えた値（ポップアップを止めるか）も開いているタブにその場で効く。`pagesShareOneProcessPool` のテストが見張っている。テストでも環境設定は一つきりなので、変えたテストは前の値に戻す。
- **`WebPage`（WebKit for SwiftUI）をやめた経緯。** 以前はページを `WebPage`、表示を SwiftUI の `WebView` で組んでいた。`WebPage` は設定にプールや `WKPreferences` を渡す口がなく、ページの案内役（`WKUIDelegateAdapter`）は `window.open` の窓を作る手続きを持たず、戻る・進むの履歴を書き出す口もない。前の二つは `WKWebViewConfiguration` の `init` の差し替えと、案内役の型への手続きの追加という実行時の裏技で埋め、外れていないかを起動後の最初のページで確かめる仕組みまで持っていた。最後の一つは埋められず、再起動やタブを眠らせると履歴が消えるため、`WKWebView` を `Page` で包む作りに移した。代わりに、SwiftUI にそのまま載る手軽さを手放し、Web ビューの値を Observable に写す層（`Page`）と画面に置く部品（`PageView`）を自分で持つことになった。`WebPage` が黙って面倒を見ていた所もこちらで埋める必要があり、移したときには、読み終えた知らせの時点で題名がまだ空のことがある件と、macOS の `takeSnapshot` が見えている所しか描かない件を直した。`WebPage` にプールと環境設定を渡す口、`window.open` の受け口、履歴の書き出しが揃えば戻すことを考えてよい。逆に、`WebPage` では起きなかった不具合が普段使いで続くようなら、この判断を見直す。
- **`window.open` はページの案内役が受ける。** `Page` の UI delegate の `createWebViewWith` から `PopupWindows.create` を呼ぶ。大きさを指定して開いたもの（ログインの小窓など）は、WebKit が渡した設定で `Page` を作って AppKit の小窓（`PopupWindow`）に置き、その Web ビューをページへ返す。小窓の中身もタブと同じ `Page` なので、ダウンロードや `alert` などの問い合わせ、`window.close()` もタブと同じ案内役が受ける（前は小窓だけ別に Web ビューを持ち、`window.open` と `window.close()` しか受けていなかったので、小窓の中の問い合わせやダウンロードは黙って取り消されていた）。`window.close()` は案内役が `Page.Event.closeRequested` として持ち主へ知らせ、タブならタブを、小窓なら窓を閉じる。小窓の一覧（`PopupWindows.windows`）はアプリ全体で一つなので、テストでは開いた側（`opener`）で自分の小窓を見分ける。返さないと `window.opener` がつながらず、Google などのログインは「窓を開けなかった」として止まる。大きさの指定がないものは新しいタブで開き、ページへは null を返す。小窓を閉じるときは Web ビューを窓から外す。閉じた窓は AppKit がしばらく掴んでいて、中に置いたままだとページが残り、開いた側から `window.closed` が false に見えた。止めるかどうかは WebKit がその手前で `javaScriptCanOpenWindowsAutomatically` を見て決めるので、止めていれば操作の中から開いたものしか届かない。スクリプトが押した `target="_blank"` のリンクも同じく WebKit が止める。`eval` と `click` は WebKit が操作の中として扱うので、止めていても開く。`popupsFollowTheSetting`、`sizedPopupsOpenInTheirOwnWindow`、`popupsHandleDownloadsLikeTabs` のテストが見張っている。設定はプロファイルによらずアプリ全体で一つで、普段使いの実体だけ `Hane/settings.json` に書き、使い捨ての実体とテストでは保存しない。
- **サイトのアイコンは自分で取りに行く。** `WKWebView` にはアイコンを渡す公開の API がない（定義ファイルで favicon が出てくるのは古い `WebView` だけ）。そこでページを読み終えるたびに、ページのスクリプトから触れない場所（`.defaultClient`）で `<link rel="icon">` と `apple-touch-icon` の候補を読み、32ピクセルに近いものを選んで、クッキーもキャッシュも持たない別の通信で取りに行く（候補がなければ `/favicon.ico`）。WebKit のプロセスに頼まないので、取った分はページの通信にもサイトデータにも残らない。32ピクセル四方の PNG に縮めてサイト（ホストとポート）ごとに覚え、保存先があればプロファイルの `favicons/` に書き、眠っているタブやブックマークは要るときに一つずつ読む。同じサイトでもパスの一段目でアイコンが違うもの（docs.google.com のドキュメントとスプレッドシート）は、サイトと違うときだけ一段目でも覚える。一段目ごとに全部覚えると、記事ごとにパスの違うサイトでファイルが増え続けるため。同じアイコンはこの実体の中では取り直さず、次の起動で一度だけ取り直す。見張りはキーごとの小さな Observable にしてあり、どこかのアイコンが届いてもほかのタブは描き直さない。ページの中でアイコンを書き換える（未読の数を出すなど）のは追わない。`FaviconTests` が見張っている。

- **ページが利用者に求めるものは、案内役で受けないと WebKit が黙って取り消す。** `alert` は何も出ず、`confirm` は false、`prompt` は null、ファイルの選択はキャンセル、表示できない型や `download` 属性のリンクは読み込みが打ち切られるだけで何も保存されない（エラー 102 として届く）。一時期どれも受けておらず、気づかなかった。いまは `Page` の案内役が受け、問い合わせは `PageDialogs` が窓のシートで出し、ダウンロードはアプリ全体で一つの `Downloads` が引き受ける。窓に載っていないページ（裏のタブ）の問い合わせは、取り消したものとして答える。ファイルの選択のシートは別のプロセスが描くので、`ui-snapshot` に中身が出ず、hanectl からは答えられない。`file://` のページは互いに別のオリジンで、別のオリジンへの `download` 属性は無視されるので、テストでは `data:` のリンクで試す。`PageDelegateTests` が見張っている。
- **カメラとマイクは Info.plist のわけの文言がないと使えない。** `NSCameraUsageDescription` と `NSMicrophoneUsageDescription` がないと、WebKit はページに `navigator.mediaDevices` そのものを見せない（エラーにもならず、サイトは「カメラがない」として振る舞う）。使わせるかどうかの問い合わせ（`decideMediaCapturePermissionsFor`）は案内役で受けておらず、そのときは WebKit が自分で尋ねる。`swift test` の実行ファイルには文言がないので、テストからは確かめられない。

## プロファイル

- **実体とプロファイルは別のもの。** 実体（プロセス）を分けるのは開発や計測で普段使いに触れないためだけで、環境変数 `HANE_INSTANCE`（dev、bench など）で選ぶ。名前を付けた実体は何も保存しない使い捨てで、操作用ソケットは `Hane/instances/<名前>/control.sock`、広告ブロックのコンパイル結果は `~/Library/Caches/Hane/instances/<名前>` に分ける。前は `BROWSER_PROFILE` が実体とプロファイルを兼ね、プロファイルごとに実体を起こして一つの窓に見せかけていたが、窓の枠の受け渡しや前に出る権利の譲り合いなど後始末が積もったのでやめた。前の変数（名前を Hane にする前の `BROWSER_INSTANCE`、`BROWSER_PROFILE`、`BROWSER_EPHEMERAL`）が付いていると、アプリも `hanectl` も止まる。黙って普段使いの実体を相手にしないため。
- **プロファイルは窓一枚に一つずつ出す。** `BrowserModel` が窓（`BrowserWindowSlot`）ごとに出すプロファイルを決め、窓に出ているプロファイルの `TabStore` を持つ。同じプロファイルは二枚の窓に出さない（閲覧状態やブックマークを書き合うため）。ほかの窓に出ているものを選ぶと、その窓を前に出すだけにする。窓の中で切り替えると、離れる `TabStore` を `shutDown()`（閲覧状態を書き出してから全ページを閉じ、以後は新しいタブも閲覧状態の書き出しも断る）し、離れるプロファイルが開いた小窓も閉じて、移る先の `TabStore` を閲覧状態から作る（選んでいたページだけ読み込む）。窓を閉じたときも同じく閉じるが、最後の窓のときは残す（Dock から開き直した窓に戻す。窓が一枚きりだった頃と同じ振る舞い）。離れたプロファイルのページは生かしておかない（切り替えは頻繁でないため）。ページの判断は非同期なので、離れたあとに古い `TabStore` へ新しいタブの頼みが届くことがあり、`shutDown()` の印で断っている。メニュー・`LocalShortcuts`・`ControlService` は最後に前へ出たプロファイルの窓（`current`）の `TabStore` を相手にし、起動時の `TabStore` を掴まず、使うたびに `model.store` を読む（掴むと切り替えたあと古いプロファイルを相手にする）。窓は自分のプロファイルの `TabStore` を `model.store(in:)` で読む。掴み残しは `switchingReleasesThePagesOfTheProfileLeft`、窓ごとの振る舞いは `eachWindowShowsItsOwnProfile` などのテストが見張る。
- **最初の窓は `Window`、二枚目からは `WindowGroup`。** 全部を `WindowGroup` にすると、`hanectl` のように裏で直に起こしたとき、起動したときの窓が作られなかった（`open` で起こしたときは作られる）。⌘N と、起動したときに戻す二枚目からの窓は `WindowGroup`（識別子 `more`）で開く。どちらの窓も中身は同じで、出すプロファイルは窓が出たとき（`BrowserModel.attach`）に決める。起動したときは覚えていたプロファイルを最初の窓から順に出し、残っていれば窓が出るたびに次の窓を開く。窓をすべて閉じたあとに開いた窓には閉じる前のプロファイルを、それ以外の ⌘N の窓にはプロファイルを選ぶ画面を出す。
- **次の起動で戻す窓は、終了の途中で窓が閉じても変えない。** 終了するときは `willTerminate`（`saveBeforeQuit`）のあとで窓が閉じる知らせが来るので、そのまま窓の一覧から外すと、次の起動で窓が一枚しか戻らない。`saveBeforeQuit` で印を付け、それ以後に閉じた窓では何もしない。窓が二枚以上のときだけ、一覧（`profiles.json` の `lastWindows`）に窓の並びを書く。
- **プロファイルの持ち物は、一度開いたら実体が終わるまで捨てない。** ブックマーク、履歴、閲覧状態、サイトデータの置き場（`ProfileData`）を名前で引けるように持ち続け、戻ったときに同じものを使う。同じファイルを二つのストアが書き合わないためと、使い捨ての実体でも閲覧状態を戻せるようにするため。
- **置き場。** 普段使いの実体では、`default` の持ち物は `~/Library/Application Support/Hane/` 直下（分ける前からの場所）、それ以外は `profiles/<名前>/` に置く。サイトデータは `default` が WebKit の既定、登録したものは一覧（`Hane/profiles.json`）に残した識別子で `WKWebsiteDataStore(forIdentifier:)` に分ける（同じ識別子なら同じものが返る）。一覧には最後に開いたプロファイル（`lastOpened`）も残し、次の起動でそれを開く。設定と隠した要素はアプリ全体で一つで、`Hane/` 直下にだけ置く。テストで `forIdentifier` を使うと `~/Library/WebKit` の下に本物の置き場ができて消せないので、テストのサイトデータは `.nonPersistent()` にする（`BrowserModel` の `keepsSiteData: false`）。
- **使い捨ての実体のプロファイル。** 登録した一覧は見せず、作った名前はその実体の中だけに持ち、どのプロファイルも何も保存しない（サイトデータは名前ごとの `.nonPersistent()`）。
- **既定のブラウザとして受けるリンク。** ほかのアプリで踏まれたリンク（http と https）は、メニューと同じく最後に前へ出たプロファイルの窓に開く（`ExternalLinks`）。選んでいるタブが開いたばかりの空のタブならそこで、それ以外は新しいタブで開く。受け口は Apple イベントの GetURL で、AppKit が起動の途中で置く受け口を `willFinishLaunching` で差し替えている。窓をすべて閉じていれば、窓を開く手段が SwiftUI の画面の中にしかないので、Dock と同じ開き直しの頼み（reopen）を自分に送って窓を出す。受け持つと宣言するのは置いた方（`~/Applications/Hane.app`）だけで、`bundle.sh` が `build/Hane.app` からは宣言を外す。同じバンドルIDなので、残すと既定のブラウザの候補に二つ並び、リンクで `build/Hane.app` が環境変数なしの普段使いの実体として起こされうる。それでも動いている開発用の実体へ届くことはあるので、開発用の実体は受けずにログへ残すだけにする。設定の窓の「既定にする」も同じ理由で開発用の実体では押せない（`DefaultBrowser`。押すと macOS が確かめる窓を出す。持ち主の既定のブラウザが本当に変わるので、試しに押さない）。開発用の実体で試すときは、`open -a` だとバンドルIDで普段使いの実体へ届くことがあるので、pid を指して GetURL を送る。
- **裏に起こす実体には記述子を渡さない（`spawnDetached`）。** 渡すと呼んだ側の操作用ソケットを子が握り、呼んだ側が終わったあとも同じパスへの接続を子が受けたまま答えない。`hanectl` は応答を待ち続け、`verify.sh` が始めの `quit` で7分止まった。

## 広告ブロック

- **広告ブロックは WebKit のコンテンツブロッカーで行う。** 判定はページのプロセスの中で WebKit がするので、アプリ側で常に動く処理はない。同梱のリスト（EasyList と AdGuard Japanese）を起動時に訳してコンパイルするのは中身か `FilterList.version` が変わったときだけで（数秒）、ふだんは `WKContentRuleListStore` から引くだけ。訳し方を変えたら `FilterList.version` を上げる。普段使いの実体は WebKit の既定の置き場、使い捨ての実体は `~/Library/Caches/Hane/instances/<名前>` に置くので、`verify.sh` の初回はコンパイルを待つ。リストはアプリ全体で一つで、プロファイルを切り替えても作り直さない。
- **WebKit のルールは1リスト15万件まで、ひとつでも受け付けないルールがあるとリスト全体が落ちる。** 訳せない書き方は捨てる方へ倒し、`bundledListsCompile` のテストで同梱のリストが実際にコンパイルできるかを見張っている。例外（`ignore-previous-rules`）は同じリストで前にあるルールしか取り消せないので、例外は最後に並べる。
- **止めた読み込みは、どこにも記録されない。** WebKit は止めたことをアプリに知らせる公開の口を持たず、Resource Timing にも残らない（つながらなかった読み込みも同じ）。`hanectl requests` の `not loaded` は、要素が指しているのに記録がないものから推し量っている（「通信の記録」は `docs/hanectl.md`）。手元のサーバーで試すときは、同梱の EasyList の `/300x250b.` が種類を問わず止めるので、`300x250b.png`、`300x250b.css`、`300x250b.html` のような名前で画像・スタイル・フレームを作れる（スクリプトなら `/js/flyad.js`）。
- **右クリックのメニューには項目を足せない。** WebKit for SwiftUI の `webViewContextMenu` は標準の項目（コピー、調べる、Webインスペクタなど）をすべて置き換えてしまう。そのため要素を隠す操作は、ページ内のスクリプトで ⌥ 付きの右クリックだけを拾っている。子フレームの中なら `postMessage` で親へ知らせてフレームごと選ばせる。`hanectl` からは、`page-click --right --with opt <番号>` で本物の ⌥右クリックとして起こし、`page-key up`・`down`・`return`・`escape` で親へ・子へ・隠す・やめるを選べる。

## 1Password

- **1Password の拡張は載せず、CLI（`op`）を押したときだけ起こす。** `WKWebExtension` で Safari 版の拡張を読む道もあるが、拡張の裏の処理が数十MB以上で居座り、拡張と本体アプリのやりとりは Hane では中継できない。`op` なら常駐するものが増えず、解錠も本体アプリの Touch ID に任せられる。入れるのは ⌘\ か鍵のボタンを押したときだけで、候補はページのホスト（とその親ドメイン）に合うログインに絞る。
- **アカウントがいくつもあると、`op` は `--account` なしでは答えない**（「multiple accounts found」）。そこで `op account list` で全部のアカウントを引き、アカウントごとに一覧を尋ねて合わせる。中身を尋ねるときも、そのログインのアカウントを付ける。答えないアカウントがあっても、ほかが答えればそれで出す。
- **初めて Hane から尋ねたときは、1Password 本体がアカウントごとに許可を求め、通すまで `op` は返らない。** 待っているあいだはボタンが回り続ける。ターミナルで許可してあっても、Hane からは別に求められる。
- **一覧は一つのアカウントで数百KBある。** 管の受け皿（64KB）を超えるので、`op` の終わりを待つ前に出力を読み切る。逆にすると互いに待って止まる。
- **アプリは Finder や Raycast から起きると `PATH` に Homebrew が入らない。** `op` は `/opt/homebrew/bin` と `/usr/local/bin` を決め打ちで探す。

## hanectl と窓まわりの操作

- **SwiftUI はアクセシビリティの木を問われるまで作らない。** `open` で起動すると常駐する何かが問い合わせて木ができるが、直に起動すると（`verify.sh`）中から辿っても空のまま。`WindowElements` は外の道具と同じ API で自分に一度問い合わせて作らせている。作らせても、何もしていない間の起床回数とメモリは変わらなかった。
- **窓まわりの操作で、アプリを止めてしまうもの。** 選択欄を押す、右クリックのメニューを出すと、閉じるまでメインスレッドが止まって応答を返せない。そのため `ui-menu` はメニューを出さずに中身を引いて項目の動作を直に呼び、`ui-click` は選択欄を断る。ボタンは押されると離す事象を自分で待つので、離す事象を先に待ち行列へ積んでから押す。選択欄は選択欄の動作を送っても SwiftUI の値が変わらず、項目の動作を呼ぶ必要がある。
- **窓まわりで、作った事象では確かめられないもの。** ドラッグは始まらない（運ぶ中身を載せた情報を落とし先へ直に渡す方法も試したが、SwiftUI は受け付けず、その後の描画でアプリが落ちた）。並べ替えは `TabStore.drop` の単体テストで見る。`onHover` はアプリが前面のときしか効かないので、裏にいるときの `ui-hover` は乗せたときの表示を出せない（`verify.sh` はそのとき skip と出す）。
- **ページへの本物の入力は、事象の種類で渡し方が違う。** 押す事象とキーは Web ビューのメソッドを直に呼ぶ（窓の `sendEvent` を通すと、裏にいるときクリックがページへ届かなかった）。ポインタの動きは直に呼ぶと届かず、窓を通す。そのうえ裏にいると WebKit が捨てるので、`page-hover` は前面でしか効かない。キーは離す事象まで送らないと `KeyNavigation` が押しっぱなしとみなし、`j` のスクロールが止まらない（`key` もこれで、窓の `performKeyEquivalent` を Web ビューが拾ってページへ渡すので、どの道でも最後に離す事象を直に渡す）。ページの右クリックのメニューや選択欄を本物のクリックで出すと、持ち主の画面にメニューが出たままになるので、`page-click` は出たそばから閉じる。回り始めの知らせの中で `cancelTracking` しても閉じず、一拍おく必要があった。
- **`xcrun --show-sdk-path` の定義ファイルと、ビルドに使う SDK が違う。** `xcrun` はコマンドラインツールの SDK（macOS 27）を指すが、`swift build` は `xcode-select` の Xcode 26.5 の SDK でビルドする。前者にだけある API（`WKJSHandle` など）は、定義ファイルにあってもコンパイルが通らない。コマンドラインツールの方でビルドしようとすると、SwiftUI のマクロの部品がなくて通らない。そのため iframe の中を引く口（`FrameHandles`）は、公開されている名前で呼んでいる（「iframe の中」は `docs/hanectl.md`）。
- **シートが出ていると終了が黙って取りやめになる。** `quit` は先にシートを閉じてから終える。終わったつもりで古い版が動き続け、作り直した版を試したつもりになることがあった。また、起動していないときの `quit` は何もしない（前は起こしてから止めていて、作り直している最中の古い版が動き出すことがあった）。

## テスト

- **テストはネットワークに出さない。** HTMLは一時ファイルに書いて `file://` で開く。`data:` や検索語はアドレスの解釈に巻き込まれやすい。
- **テストのプロセスが総括を出さずに終了コード 0 で終わることがある。** テストの主スレッドは Swift の非同期の入口が回す素の `CFRunLoopRun` で、これが返るとプロセスが終わる。AppKit がイベントを待っている間（`page-click` で選択欄のメニューを出している間など）にウインドウサーバーからイベントが届くと、HIToolbox は主スレッドを起こすため `CFRunLoopStop` を呼ぶブロックを積む。そのブロックが走る前にメニューが閉じると、止める先が外側の素の回しになって終わる。窓を作るテストが並んで走るほど起きやすく、全部のテストを走らせると前からほぼ毎回これで途中で終わっていた。アプリでは `NSApplication.run` が回し直すので害はない。テストでは窓を扱うスイートの初めに `MainRunLoop.keepRunning()` を呼び、止められても回し直す回しを run loop のブロックとして一段内側に置く（主キューのブロックの中で回すと、その間 MainActor の仕事が進まず止まった）。
- **`file://` のページでは例外の中身が「Script error.」に潰れる。** WebKitの仕様で、http(s) のページでは普通に取れる。
- **`file://` の資源は Resource Timing に記録されない。** 記録に出るのは各フレームのページ本体（navigation）と http(s) の資源だけなので、`requests` の単体テストで記録の行として確かめられるのはページ本体まで。資源の行は手元のサーバーを立てて `hanectl` で見る。
