# hanectl で動かして確かめる

命令の一覧と書き方は `build/hanectl help`（`ControlHelp` が正本）。ここには、仕組みと、なぜそうなっているかを残す。

## 起こし方と実体

`HANE_INSTANCE=dev` の実体は、操作用ソケットが別で（`~/Library/Application Support/Hane/instances/dev/control.sock`）、Cookieなどを保存しない使い捨てになる。前の書き方の `BROWSER_INSTANCE`、`BROWSER_PROFILE`、`BROWSER_EPHEMERAL` が付いていると、`hanectl` もアプリも止まる（黙って普段使いの実体を相手にしないため）。起動していなければ `hanectl` が隣の `build/Hane.app` の実行ファイルを直に、別のセッションで起こすので、前に出て持ち主の作業を遮ることはない（`open -g` で裏に起こすと SwiftUI が窓を作らない）。前に出したいときは `HANE_LAUNCH=front`。直に起こすときは、アプリを端末ではなく自分自身の責任プロセスにしている。端末から起こした実体どうしで WebKit の補助プロセスの持ち主が同じになると、`stats` が別の実体のプロセスまで数えてしまうため（`verify.sh` もこのため `hanectl` に起こさせる）。`bench.sh` は前の結果と比べられるよう前面で測る。`ui` の二行目に pid と起動した時刻、実行ファイルを作った時刻が出て、起動のあとに作り直していれば古い版が動いていると書く。ページだけを撮るなら `hanectl screenshot <保存先>`。`window-screenshot` を `cacheDisplay` で作ると、バーの背景が明るい外観の白で塗られて実物と違ってしまうので、層を直に描いている。撮った画像を `sips -c` で切り抜くと真ん中が切り出されるので、縮めて見るなら `sips -Z 1200`。

## 入力とキー

アドレスバーへの入力は `hanectl type <文字列>` で打てる（`--replace` で今の中身を置き換える）。キーの事象を作ると持ち主の入力方式が日本語のとき仮名に化けるので、入力欄の編集部品へ文字を直接差し込んでいる。履歴から補った続きは `ui` の `completion=` に出る。

メニューやバーへのキー操作は `hanectl key cmd+1` のように送れる。アプリが裏にいるとシステムはキーを届けず、前に出すと持ち主の作業を遮るので、`WindowInput` が窓の部品のキー、メニュー、ウインドウの順を自分で辿って手渡しする（ページにフォーカスがあるときの ⌘ や ⌃ のキーだけは、Web ビューが先に飲んでメニューへ届かないので、アプリの事象の道 `NSApp.sendEvent` に載せる）。宛先は、本体の窓より手前に設定の窓が出ていればそれ、なければシート、ポップオーバー、窓の順に出ているものを選ぶ。前面にいるときも同じ道を通す（待ち行列に積むと、アラートの Return と Esc が効かなかった）。ただし既定のボタン（アラートの OK など）が Return に応じるのは、その窓がキーを受ける窓のときだけで、裏にいるアプリの窓はキーを受ける窓になれない（`makeKey` しても変わらなかった）。そのため裏では、アラートのシートが出てから何秒待っても Return で閉じなかった（窓の中を一度クリックしたあとなど、アプリの中でキーを受ける窓になっていれば効くので、効いたり効かなかったりに見えた）。Esc のようにボタン自身に割り当てたキーは裏でも効く。そこで窓がキーを受ける窓でなければ、Return は既定のボタンを直に押す。同じく裏では、一度シートや選択欄のメニューを出したあとだと、キーで開いた新しい窓（⌘N の窓）が本体の窓の裏に置かれて `ui-snapshot` に出なかったので、`key` は新しく開いた窓を本体の窓のすぐ上に重ねる（ほかのアプリの窓より前には出さない）。

## ページへの本物の入力

`click`、`fill`、`press` はページの中のスクリプトで要素を押したり事象を作ったりするので、ページからは `isTrusted` が false に見える。文字のキーでの操作（`KeyNavigation`）は合成されたキーを無視し、`window.open` を止める仕組みやホバーで開くメニュー、⌥右クリックの要素選び（`ElementPicker`）も、利用者の本物の操作でないと試せない。そこで `page-click`、`page-hover`、`page-key` は、AppKit のマウスとキーの事象を作って Web ビューへ渡す。WebKit はそれを利用者の入力として扱うので、ページには `isTrusted` が true の事象として届く。Web ビューに事象を渡すのは `Page` の受け持ちで、`PageInput` は位置を測って頼むだけにしている。

位置は CSS の画素（表示している範囲の左上から）で、`snapshot` の番号で指せば、ページの中で要素の真ん中を測ってから押す（画面の外なら真ん中へスクロールする）。ページの拡大率は `Page` が掛けて Web ビューの座標に直す。届くのは窓に載って見えている Web ビューだけなので、選択中のタブに限っている。

押す事象とキーは、窓（`NSWindow.sendEvent`）を通さずに Web ビューのメソッドを直に呼んで渡す。窓を通すと、アプリが裏にいるときクリックがページまで届かなかった（直に呼べば裏でも届き、前にも出ない）。キーは押す事象と離す事象を対にして送る。離す事象がないと、`KeyNavigation` は押しっぱなしとみなしてスクロールを流し続ける（窓まわり向けの `key` も、ページにフォーカスがあってページへ届くときは、最後に離す事象を直に渡して対にしている）。送る前に Web ビューへフォーカスを移すので、アドレスバーにフォーカスがあってもページに届く。

ポインタの動き（`page-hover`）だけは逆で、Web ビューの `mouseMoved` を直に呼んでも届かず、窓を通すと届いた。さらにアプリが裏にいると、どちらの道でも WebKit は動きを捨てる（`ui-hover` と同じく前面でしか確かめられない）。ただし押す事象はポインタの位置も動かすので、裏でも `page-click` のあとはその位置がホバーされた状態になる。

右クリックのメニューと選択欄の選択肢は、WebKit がページの返事を待ってから出し、出ている間はメインスレッドがメニューの中を回り続ける（応答は返せるが、持ち主の画面にメニューが残る）。そこで `page-click` の間だけメニューが回り始める知らせを見張り、出たら項目を控えてすぐ閉じる。知らせの中で閉じても効かなかったので、一拍おいて閉じている。⌥右クリックは要素選びのスクリプトが既定の動作を止めるので、メニューは出ない。

## iframe の中

`snapshot`、`click`、`fill`、`press`、`page-click`、`page-hover` と、`--frame` を付けた `text` と `eval` は、iframe の中でも走る。スクリプトを特定のフレームで走らせる公開の口は `callAsyncJavaScript` の `in:` に渡す `WKFrameInfo` だけで、これは自分では作れず、WebKit から受け取るしかない。受け取る道は、ページからの知らせ（`WKScriptMessage.frameInfo`）や読み込みの案内役に付いてくるものが前からあったが、どれも普段の閲覧の側でフレームごとに知らせを送らせるか、フレームの一覧を持ち続ける必要があった。そこで macOS 27 の WebKit に入った `WKJSHandle` を使う。`hanectl` の実行環境（`PageScripting` の `world`）を `createJSHandle` を許した設定で作っておき、命令が来たときだけ、親のフレームで `window.webkit.createJSHandle(iframe.contentWindow)` を返させ、アプリでそれをフレーム（`windowProxyFrame`）に引き直してから、そのフレームで同じスクリプトを走らせる。別のオリジンのフレームでも、ページのスクリプトからは中に触れないが、アプリからはこの道で引ける。普段の閲覧には何も足していない（全フレームへのスクリプトも、フレームごとの知らせもない）。macOS 26 にはこの口がなく、ほかに子フレームを引く公開の道もないので、26 では iframe の中へ下りず、`snapshot` や `requests` ではそのフレームを「中を読めなかった」と出し、`--frame` を付けた命令は断る。

フレームは毎回たどり直す。`snapshot` は主フレームから順に、見えている iframe を並んだ順に下りて、フレームの行（`frame 1`、`frame 1.2` のように親からの順番をつないだ名前）の下に中身を字下げして並べる。番号はページ全体の通しにし、控え（`__refs`）は要素のあるフレームが番号の位置に持つ。主フレームはどの番号の範囲がどのフレームにあるか（`__frameRefs`）だけを持ち、`act` と `locate` は主フレームで走ってその番号が子フレームのものなら道筋を返し、アプリがそのフレームで走らせ直す。道筋は iframe の並びの順番なので、`snapshot` のあとに iframe が増えたり減ったりすると別のフレームに着くことがあるが、そのフレームの控えにはその番号がないので「取り直すこと」と断る。番号を付けない `press` は、主フレームでフォーカスが iframe にあればその中へ下りる。

`page-click` の位置は、子フレームの中で要素の真ん中を測り、外側へ向かって各段の iframe の中身の左上（枠と内側の余白を足したもの）を足して主フレームの位置に直す。中でスクロールすると外側も動くことがあるので、測り終えてから iframe の位置を測り直す。途中のフレームの表示している範囲から外れていれば押さない。iframe に CSS の変形（`transform`）が掛かっていると位置がずれる。

## 通信の記録

`requests` は、ページが自分で持っている読み込みの記録（Resource Timing。`performance.getEntriesByType` の navigation と resource）を、命令が来たときだけ各フレームで読む。普段の閲覧の側では、fetch や XHR を差し替えたり、リクエストごとにアプリへ知らせたり、一覧を持ち続けたりしない。フレームは「iframe の中」と同じ道で辿るが、広告のフレームは見えない大きさや `display: none` で置かれることが多いので、ここだけは見えていないものも辿る（`frame` のスクリプトに `every` を渡す）。見えているものは `snapshot` と同じ番号にそろえ、見えていないものは `frame h1` のように別に名付ける。時刻はフレームごとに起点（`performance.timeOrigin`）が違うので、主フレームの起点からの時刻に直してから並べる。

広告ブロックで止めたものを WebKit が知らせる公開の口はない（定義ファイルにあるのはルールリストのコンパイルと付け外しだけ）。止められた読み込みは Resource Timing にも残らず、手元のサーバーにも届かなかった。そこで、要素が指しているのに記録がないものを `not loaded` として拾う。止められた画像は読み終えた扱い（`complete`）なのに大きさが 0、スタイルシートは `sheet` が null、iframe は about:blank のまま残るので、それで失敗と分かる。スクリプトの要素には状態がないので、http(s) で記録がないことだけで決める。ただ、つながらなかった読み込みも記録に残らないので、止められたものと見分けられない（iframe だけは、つながらないとエラーのページになって中を覗けず、about:blank と区別できる）。スクリプトが fetch や XHR で頼んで止められたものは、指している要素がないので拾えない。これらを拾うには、普段の閲覧で読み込みを見張り続けるか、WebKit の非公開の知らせに頼るしかなく、どちらもしていない。

記録には WebKit の決まりがある。file: の資源（スクリプトや画像）は記録されないので、`not loaded` は file: のものでは状態で失敗が分かる要素だけを見る。資源の記録は一つの文書で 250 件までで、あふれた後の読み込みは捨てられる（ページが `setResourceTimingBufferSize` で広げていなければ）。あふれたフレームにはそう書き添え、`not loaded` に読み込めていたスクリプトが混じることがある。読み込み直したとき、キャッシュから読んだ iframe の行が親の記録に出ないことがあった。

## 条件を待つ

`wait --text / --selector / --js` は、読み込みのあとにスクリプトが描く画面を待つための命令で、`eval` を繰り返さずに済む。命令が来たあいだだけ、100 ミリ秒おきにページへ尋ねる（本文の文字列と見えている要素の数は `hanectl` の実行環境、`--js` は `eval` と同じくページの環境で）。MutationObserver を掛ける手もあるが、フレームをたどり直す道や `--js` の式と合わせるには、尋ね直すほうが単純で、返ったあとに何も残らない。常駐のタイマーも普段の閲覧への仕掛けもない。

尋ねる仕事は別の `Task` で走らせ、待つ側はその返りを待たずにシートと時間切れを見張っている。アラートのシートが出るとページのスクリプトが止まって返らなくなるので、返りを直に待つと `wait` ごと固まるため。シートが出ていれば、それを理由に失敗にする（置き去りにした尋ねは、シートに答えれば終わる）。読み込みが始まったら尋ねるのをやめて、終わってから続ける。移る前のページから返った結果は捨てる。時間切れの上限は、`hanectl` が落ちる 120 秒より短い 100 秒。

## アプリ自身の記録

`app-logs` は、アプリが保存の失敗や起動のとりやめなどで出す記録（`AppLog`）を、命令のときだけ `OSLogStore(scope: .currentProcessIdentifier)` で読む。記録を溜める仕組みは足していない。以前の `NSLog` は、文面が統一ログに `<private>` としか残らず（動かして確かめた）読めなかったので、subsystem つきの `Logger` に置き換え、埋める値に `privacy: .public` を付けた。同じプロセスの名で WebKit などが大量に出すので、読むときは subsystem で絞る。`Logger` は stderr に出さないので、端末から実行ファイルを直に起こしても、この記録は端末には出ない。

読むのは、記録の量によらず 1 秒近くかかる（尋ねる範囲を狭めても変わらなかった）ので、メインスレッドを止めないよう別のタスクで読む。読めるのはこのプロセスが起きてからの分だけで、起こし直すと前の分は消える（保存した記録を見るには `log show` を使う）。

## 窓まわりの部品

窓まわりの部品（タブ、ブックマーク、ボタン、ポップオーバーやアラートの中身）は、`ui-snapshot` で一覧を取り、`ui-click`、`ui-hover`、`ui-menu`（右クリックのメニューと選択欄）で触る。部品は番号か名前で指す。名前なら窓から拾い直すので、並びが変わったあとに古い番号で別の部品を押す取り違えが起きない。同じ名前が重なると候補を出して断るので、`tab:Second` や `button:新規タブ` のように種類を付ける。部品はアプリ自身のアクセシビリティの木から拾い、操作は部品の真ん中へマウスの事象を作って窓へ渡す（`WindowElements`）。タブとブックマークは画面の側でアクセシビリティの識別子（`tab`、`bookmark`）を付けたまとまりにしてあり、項目ごと一行で出る。幅で見た目が変わる部品は `window-size`、外観は `appearance dark|light|system` で切り替えて `window-screenshot` で撮る。設定の窓（`key cmd+,` で開く）やポップアップの小窓のように別に開く窓も、本体の窓より手前にあれば `ui-snapshot` に続けて出て触れる。ただし設定の窓の Form の中身は、層を直に描いても `cacheDisplay` でも写らなかった（白いまま）ので、見た目は部品の一覧で確かめる。

```sh
build/hanectl ui-snapshot              # [2] bookmark "二番" @167,3 42x26、[3] tab "Second" … など
build/hanectl ui-menu bookmark:二番     # 右クリックのメニューの項目
build/hanectl ui-menu 二番 名前を編集…   # 選ぶとポップオーバーが出て、ui-snapshot に中身が続く
```

## 普段使いの版で試してもらう

持ち主が普段使いで試すのは `~/Applications/Hane.app` で、`build/` を作り直しただけでは変わらない。試してもらう前に `scripts/bundle.sh --install` し、動いている実体を ⌘Q で終えて起動し直してもらう（タブは前回の閲覧状態から戻る。ただし入れ替え前の版で終えたときは、その版が状態を書き出していないので戻らない）。入った版は `cmp ~/Applications/Hane.app/Contents/MacOS/Hane build/Hane.app/Contents/MacOS/Hane` で確かめる。

## 窓の副作用を見る

修正が窓まわりに副作用を出していないかは `hanectl ui` の `window frame:` で見る（大きさ、画面の左上からの位置、覚えている名前）。
